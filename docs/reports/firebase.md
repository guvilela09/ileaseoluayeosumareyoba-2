# Integração Firebase preparada

`src/lib/auth.js` fornece `createAuth(config)` com login Google/e-mail, cadastro com nome/verificação, recuperação, senha mediante reautenticação, sessão, upload privado e presença por conexão. Colisão entre provedores apresenta orientação para entrar pelo método original; não associa credenciais automaticamente. A consulta `getPresence()` é administrativa; sem DATABASE_URL devolve mapa vazio. Cada navegador remove somente a própria conexão ao sair.

`firebase/firebase.json` aponta regras e Functions Python 3.12; deploy usa a pasta `firebase` como diretório de projeto. Firestore não permite writes de clientes, e-mail não verificado, pendentes ou bloqueados; membros só consultam comunicados publicados, conteúdo ativo, perfil próprio e progresso próprio. Storage admite criação de imagens próprias de até 5 MB; importações até 10 MB somente por administrador. O backend valida novamente bytes, tamanho e origem ao registrar. Não usar `getDownloadURL` em importações: no registro, remover metadata `firebaseStorageDownloadTokens` eventualmente gerada pelo serviço; URL de imagem assinada expira.

Mirror RTDB `serverMirror/approvedUsers/{uid} = {approved:boolean,admin:boolean}` é exclusivo do servidor. Backend deve atualizar imediatamente quando status/papel muda; `reconcile_access` repara alterações externas. Claims `role` e `approved` preservam as demais claims e não substituem perfil Firestore como fonte de autorização. Bloqueio deve também apagar presença daquele UID; reconexões falham pela regra.

Publicação cria `mailCampaigns/{announcementId}` com `announcementId,title,content,createdAt,status:'queued',requestedBy`. O trigger congela UIDs elegíveis, gera `deliveryJobs` com IDs SHA-256 determinísticos e enfileira uma tarefa por pessoa. Edição não cria nova campanha. Recuperação administrativa cria `passwordResetJobs/{uniqueId}` com `uid,status:'queued',requestedBy,createdAt`. O link permanece na outbox privada e nunca vai ao navegador; Google sem senha recebe status `skipped`.

Worker `deliver_email` é privado, tem limite de 1 dispatch/s, 2 concorrentes, 5 tentativas de envio e envelope persistido. Resend recebe um único destinatário e `Idempotency-Key` estável. A fila pode repetir eventos sem recriar envio. Após 23 horas ou falha final indeterminada, o registro fica `uncertain` para reconciliação manual, pois chaves Resend expiram em 24 horas. `sent` significa aceitação pela API Resend com ID do provedor; não comprova entrega à caixa postal. Não há webhooks de entrega nesta versão. Importações ganham expiração de 24 horas no registro privado e a API recusa a prévia ao vencer. A função agendada exclui arquivos registrados e também examina páginas de até 1000 objetos do Storage, removendo envios `kind=import` órfãos com mais de 24 horas. O cursor privado em Firestore permite continuar a varredura na próxima hora. Fotos permanecem até serem substituídas.

`recover_queued_outboxes` roda a cada 15 minutos e retoma campanhas/recuperações parciais e jobs cuja criação de task falhou. `prune_expired_imports` roda a cada hora, remove até 500 arquivos vencidos registrados e examina até 1000 objetos por página para encontrar envios abandonados. Firebase Functions Python 0.6 não expõe configuração de retry nos decorators Firestore; a outbox durável e esse sweep evitam perder disparos após falha transitória. As tarefas agendadas usam Cloud Scheduler; considerar esse serviço e seus custos na configuração do projeto. Limites por execução de recuperação: 100 campanhas e 100 recuperações, 1000 jobs sem task confirmada.

Presença versiona cada conexão com a revisão do documento de acesso. A regra RTDB exige que o token e o mirror tenham a mesma revisão antes de aceitar uma nova conexão. Ao bloquear alguém, o servidor remove atomicamente apenas conexões com revisão antiga, preservando uma conexão criada depois de eventual reaprovação. A sincronização repete a leitura de perfil e claims quando o documento muda durante a operação; a presença não depende de ordenar chamadas distribuídas entre Auth, Firestore e RTDB.

## Preparação e publicação futura

Nenhum projeto, conta, credencial, faturamento ou envio real foi criado/ativado.

1. Criar projeto Firebase, Auth Google/e-mail, Firestore `(default)`, RTDB e bucket Storage. Storage/Functions/Cloud Tasks precisam de plano e faturamento compatíveis. Escolher região conscientemente; Functions do código estão em `us-central1`.
2. Registrar Web App, preencher variáveis públicas FIREBASE_* do backend, autorizar o domínio Vercel em Auth e configurar domínio verificado Resend. Credenciais Admin somente no backend; localmente use Application Default Credentials ou GOOGLE_APPLICATION_CREDENTIALS fora do repositório.
3. Dentro de `functions`, criar `venv` Python 3.12 e instalar `requirements.txt`. Dentro de `firebase`, copiar `.firebaserc.example` para `.firebaserc` com o ID real. Não versionar arquivos de conta de serviço.
4. `firebase functions:secrets:set RESEND_API_KEY`; configurar `MAIL_FROM` e `DATABASE_URL` via parâmetros do deploy. `MAIL_FROM` exige domínio Resend verificado, e DATABASE_URL é a URL HTTPS de seu RTDB. Esses parâmetros não devem estar em `VITE_*`.
5. `firebase deploy --only firestore:rules,firestore:indexes,database,storage,functions` a partir de `firebase`. A CLI cria fila task function. IAM do runtime precisa de Cloud Tasks Enqueuer, permissão `cloudfunctions.functions.get` (lookup da URL), invocação da task function e permissões Admin Auth/Firestore/RTDB. Use os menores papéis que suportem esses acessos; não conceda acesso a clientes.
6. Conta candidata cadastra-se no portal e confirma e-mail. Operador confere UID em Auth e executa `python scripts/bootstrap_admin.py --uid UID --confirm-uid UID --project-id PROJETO --database-url URL`. Exige perfil já existente e impede escolher outro primeiro admin quando há um aprovado. Operação transacional Firestore e repetível após falha de sincronização; APIs Auth/RTDB não compartilham transação. Conta sai/entra para renovar claims.
7. Rodar suite de regras nos emuladores antes do deploy. Exige Java compatível, Firebase CLI e `@firebase/rules-unit-testing`. Dentro de `firebase`: `firebase emulators:exec --project demo-ilease --only firestore,database,storage "node --test tests/rules.test.mjs"`. Projeto `demo-*` evita acesso a produção. Testa aprovação, isolamento, writes negados, filtros de comunicados, mirror/presença e uploads.

## Verificação

Testes puros em `functions/test_mail_logic.py`: filtro de destinatários, identidade determinística, isolamento por e-mail, escape do conteúdo e limite da janela idempotente. Comando: `python -m unittest discover -s functions -p 'test_*.py' -v`.

Executados: 10 testes passaram com Firebase Functions 0.6.0 e Admin SDK 7.7.0, incluindo o handler real com Firestore/HTTP substituídos por fixtures locais: dispatch duplicado só faz um POST; retentativa reusa payload/chave; destinatário bloqueado é descartado; chave expirada impede envio; task usa envelope `{data:{jobId}}`. Renderer de e-mail gera HTML escapado a partir de Delta textual, preserva negrito/itálico/sublinhado/listas e somente fontes sans/serif, tamanhos 14/16/18/20/24/32px e cores hex de seis dígitos; ignora links/embeds/CSS arbitrário. Import e decorators/manifest de todas as Functions carregaram sem credenciais e sem rede. `node --check src/lib/auth.js` passou. Suite de regras requer emuladores reais; o relatório principal deve distinguir se foi executada na integração final.
